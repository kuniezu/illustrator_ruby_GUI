# Phase 0: アーキテクチャ評価

更新日: 2026-09-05
対象: `main` の `Illustrator Ruby GUI.jsx`、`requirements.md`、Draft PR #1 の `docs/exhibition-ruby-spec.md`
調査ブランチ: `codex/phase0-architecture-review`

## 1. 結論

現行コードは、選択した単一テキストフレームを読み取り、ScriptUI 上で文字単位の入力状態を作り、実行時に `Ruby` レイヤー内へルビ用テキストフレームを生成する、という責務分担になっている。GUI と配置計算は既に分離されており、Phase 1 の土台として再利用できる。

一方、現在の `rubyData` は実行中の `main()` にしか存在せず、生成したルビにも本文との識別情報が付かない。このため、再実行時の読み込み、`suppressed`、手動補正の保持、本文編集後の再解決は新しい永続データモデルなしには実現できない。また、ルビ配置は `createOutline()` の一時生成物と `contents` 上の文字番号に強く依存しているため、アウトラインを永続アンカーにする設計は避けるべきである。

推奨方針は次のとおりである。

1. Phase 1 は既存の配置計算を温存し、生成したルビのグループに識別可能なメタデータを付ける小さな垂直スライスから始める。
2. 永続化方式は未確定とする。`name + note` は候補として小さな実機検証を行い、正式採用はその結果を見て決める。
3. 本文へのアンカーは、フレーム識別子だけでなく、対象文字列・前後コンテキスト・旧位置・読みを持つ複合アンカーにする。候補が一意に決まらない場合は移動せず要確認とする。
4. 自動読み生成は Phase 1 に含めない。将来は解析エンジンを外部処理にできる境界を設けつつ、配布・オフライン性を優先して辞書と人間確認を中心に段階導入する。
5. しばらくは単一 `.jsx` を維持し、保存・読込・アンカー解決を独立関数として追加する。分割はテスト可能な境界が固まってから行う。

この文書は評価のみを目的とし、既存 `.jsx` の変更、機能実装、実展示原稿・辞書の追加は行っていない。

## 2. 調査対象と現行構造

Issue #2 が指定する調査項目、Draft PR #1 の展示制作向け要件、`requirements.md` の既存 GUI 要件を照合した。現行コードの主な位置は以下のとおりである。

| 責務 | 現行実装 | 評価 |
|---|---|---|
| 対象取得 | `getSelectedTextFrames()`、`main()` | 選択中の `TextFrame` を集め、複数時は先頭だけ処理する。選択の永続識別はない。 |
| GUI状態 | `showRubyGUI()` 内の `rubyData`、`selectedCharIndices`、`pageState` | UI再描画中は状態を保持するが、スクリプト終了後には残らない。 |
| 文字表示 | `contents` の行分割、`charInfoMap`、ページ単位の `renderPage()` | `characterIndex` は `contents` の位置であり、編集に弱い。 |
| グループ | `rubyData[f][index]` の leader/member | 連続文字の先頭に読みと `baseLength`、メンバーに `leaderIndex` を持つ。GUI上は同一ページ内に限定される。 |
| 配置 | `placeRubys()`、`placeOneRuby()` | 親文字の属性を参照してルビを生成し、横書きは上、縦書きは右へ配置する。 |
| 外部状態 | なし | 生成物を次回に読込むモデル、削除・更新・再解決のプロトコルがまだない。 |

データフローは次のように整理できる。

```text
Illustrator selection
  -> getSelectedTextFrames()
  -> textFrame.contents / textRange.characters
  -> 全文字の視覚行・characterIndexを作成
  -> ScriptUIの入力・選択・グループ操作
  -> rubyData[frame][characterIndex]
  -> placeRubys()
       -> Ruby layer / frameGroup
       -> frame.duplicate() / createOutline()
       -> visibleIndexMap + compoundPaths
       -> placeOneRuby()
       -> ruby text frames
```

## 3. 現行 `rubyData` と Ruby レイヤー／生成グループ

### 3.1 GUI内のデータ

個別ルビは概ね次の形で、`characterIndex` をキーに保持される。

```js
{
  mode: "individual",
  ruby: "よみ",
  individualRubys: ["よみ"],
  baseChar: "漢",
  baseLength: 1
}
```

グループは先頭文字に `mode: "group"`, `ruby`, `baseLength`, `isGroupMember: false` を持たせ、後続文字に `isGroupMember: true`, `leaderIndex` を持たせる。これは現在の一括配置には十分だが、展示向け仕様で必要な `auto` / `auto_offset` / `manual` / `suppressed`、候補の出所、確定者、スタイル、相対オフセットはない。

`main()` の再描画ループは `rubyData`、ウィンドウ情報、ページ番号、学年設定を次の `showRubyGUI()` に渡すだけであり、文書から既存ルビを復元する処理ではない。したがって、再描画と再編集可能な永続化は別問題として扱う必要がある。

### 3.2 生成物

`placeRubys()` は既存または新規の `doc.layers["Ruby"]` を取得し、フレームごとに `groupItems.add()` でグループを作る。グループ名は `ruby_` + `frame.name`（未設定時は連番）である。各ルビはそのグループ内の `textFrames.add()` で作られ、親文字からサイズ、フォント、色を取得する。

現状の名前だけでは不十分である。

- `frame.name` は空、重複、ユーザー変更があり得る。
- 同じ処理を再実行すると新しいフレーム別グループが増える。既存グループの更新・削除・重複検出の規約はない。
- ルビ自身に親フレーム、文字範囲、読み、生成時の標準位置は保存されない。
- `Ruby` は予約レイヤー名に近い運用上の規約であり、他の用途の同名レイヤーとの衝突処理も未定義である。

Phase 1 では、既存の見た目を変えずに、生成グループにスキーマ名と一意 ID を付け、グループ内の各ルビにレコードを対応させるのが最小の拡張になる。既存の名前形式を直ちに変更する必要はないが、新形式を明示的に判定できる印を追加するべきである。

## 4. 再編集用メタデータの保存方式

この節では、現行コードから直接確認できる事実と、Illustrator実機で検証が必要な候補を分ける。候補は、本リポジトリのコードで保存・再読込できることを確認したものではない。

### 4.1 現行コードから確定できる事実

- `placeRubys()` は `Ruby` という名前のレイヤーを検索し、なければ作成する。
- フレームごとにグループを作成し、`frameGroup.name` に `ruby_` + `frame.name`（または連番）を設定する。
- ルビはそのグループ内の `textFrames.add()` で作成される。
- 現行コードには `PageItem.name` や `PageItem.note` への書き込み・読み込みはない。
- 現行コードには文書内専用オブジェクト、XMP、サイドカーJSONによるメタデータ保存もない。

したがって、現在のAIファイルを閉じて再度開いた後に、現行スクリプトだけで `rubyData` を復元できるとは言えない。

### 4.2 候補と実機検証事項

| 方式 | 候補として期待できる点 | 実機で確認が必要な点 | Phase 0時点の扱い |
|---|---|---|---|
| `PageItem.name` | Illustrator内で見える短い識別子にできる可能性。 | 対象バージョンで読み書きできるか、ユーザー操作・複製・保存再開で保持されるか。構造化データの長さ・文字種制限。 | 候補。短い識別子専用として検証。 |
| `PageItem.note` | オブジェクト付随のメモ欄として構造化情報を持てる可能性。 | 対象バージョンでのAPI、JSON・Unicode・長さ、複製・コピー・保存再開後の保持、ユーザー編集。 | 候補。小さなレコードで検証。正式採用ではない。 |
| 文書内専用オブジェクト | 文書単位のインデックスをまとめられる可能性。 | 作成・非表示・ロック・削除・コピー時の耐久性、レイヤー汚染、実機での読み書き。 | 将来候補。Phase 1の初手にはしない。 |
| XMP／文書メタデータ | 文書単位で保存できる可能性。 | 利用可能API、バージョン差、サイズ、個別ルビとの対応、保存再開後の保持。 | 未評価の候補。 |
| サイドカー JSON | 大量データ・辞書・履歴を管理しやすい。 | AIとの同時移動、命名・同期漏れ、配布方法、オフライン運用。 | 将来の補助候補。単独の正本とはしない。 |

### 暫定方針

`name + note` を現段階の推奨候補とする。ただし正式採用とはせず、Phase 1の冒頭で、1件のルビを対象に書き込み、AIを閉じて再度開き、読み戻せるかを確認する。保持されない場合は、文書内専用オブジェクトやサイドカー等を再評価する。大きな辞書や監査履歴をどこへ置くかも、この検証後に決める。

概念スキーマ例（実装ではなく設計案）:

```json
{
  "schema": "illustrator-ruby/v1",
  "recordId": "uuid-or-generated-id",
  "base": {"frameId": "...", "text": "北海道", "start": 12, "length": 3,
           "before": "説明文", "after": "にある"},
  "ruby": "ほっかいどう",
  "state": "auto_offset",
  "style": "exhibition-body",
  "offset": {"x": 0.05, "y": -0.02, "unit": "em"},
  "source": "project-dictionary",
  "needsReview": false
}
```

`name` と `note` は、どちらも正本データを無制限に詰め込む場所ではない。大きな辞書や監査履歴は、将来サイドカーへ明示的に書き出す場合でも、AI内メタデータを最低限の復旧情報として残す設計が安全である。公開リポジトリには実展示原稿や実運用辞書を入れない。

## 5. 本文との再ひも付け

### 5.1 現行コードから確定できる事実

現行コードは `activeDocument.selection` から `TextFrame` を取り出し、`contents` と `textRange.characters` を処理する。`characterIndex` は `contents` の位置としてGUIと配置処理で使われるが、本文変更後に自動補正する処理はない。

### 5.2 識別子の候補と検証事項

`characterIndex` は現行GUIの処理キーとして使われているが、本文先頭への追加、文字削除、改行変更で変わる。`frame.name` は現行コードで名前に使われているだけで、安定識別子であることは確認できない。Illustratorのバージョンによって `uuid` 相当のプロパティが利用できる可能性はあるが、これは候補にすぎず、対象バージョンでの可用性と保存・複製時の挙動を実機確認する必要がある。

第一キーをフレームIDだけに固定せず、次の優先順位で候補を絞る。

1. 文書内メタデータが保持するフレーム識別子（利用可能ならIllustrator固有ID）。
2. フレームの短い本文ハッシュまたは本文スナップショットによる照合。
3. 対象文字列、旧 `start` / `length`、前後コンテキストによる探索。
4. 候補が一つに定まった場合のみ更新。0件または複数件なら `needsReview` として停止。

同じ語が文書内に何度も出る場合、対象文字列だけでは足りない。前後コンテキストを長くし過ぎると本文変更に弱くなるため、短い前後文字列と旧位置を組み合わせ、スコアリング後に一意性を検査するのが妥当である。改行や空白は正規化用の比較表現を持ってもよいが、実際の配置は原文の文字位置を使う。

`baseChar` や `text` の保存は、本文が意図せず別の文字列に変わったことを検知するために必要である。検知した場合に近い候補へ黙って移すのは危険であり、候補を提示して人間に選ばせるべきである。

## 6. `createOutline()` 依存の制約

### 6.1 現行コードから確定できる事実

現行実装はフレームを `duplicate()` して `createOutline()` を一度だけ実行し、`compoundPathItems` を全ルビで共有する。`contents` と `textRange.characters` もキャッシュし、改行・空白等でアウトラインが生成されない文字を `visibleIndexMap` でスキップしている。この最適化と一時アウトラインを `finally` で削除する処理は、既存のクラッシュ回避策として維持する価値が高い。

### 6.2 実機検証が必要な仮説・制約

次の点は、現行コードの構造から予想される制約であり、全てのIllustratorバージョン・テキスト種別で確定した事実ではない。

- `createOutline()` は表示字形の実測には有効だが、文字の論理的な範囲・字間・空白の位置を完全には表さない。
- CR/LF、Tab、半角スペース、全角スペース、emスペース等がパスを作らないため、文字番号とパス番号は一対一ではない。
- compound pathの順序、複合字形、合字、異体字、混在フォント、効果・変形・エリア文字で対応関係が不安定になり得る。
- フレームごとのアウトライン化は重い。長文・多数ルビではメモリと処理時間のリスクがある。
- 一時複製は本文を壊さないが、再編集のアンカーとして保存すると古い座標・古い字形を固定してしまう。
- 現在のフォールバックはフレーム位置と推定幅に依存するため、難しい字形や例外的な組版では精度保証にならない。

したがって、アウトラインは「その実行時の標準配置を計算するための一時測定」に限定する。永続化するのはアウトライン座標ではなく、親文字の識別情報、相対スタイル、標準配置との差分である。再配置時には現在の本文から再度アウトラインを作り、現在の標準位置を算出する。

## 7. 手動オフセットの保持

### 7.1 現行コードから確定できる事実

現行コードは標準配置を計算して `rubyFrame.left` / `top` を設定するが、生成時の標準位置をメタデータとして保存しない。また、ユーザーがルビをドラッグした後に差分を収集する処理、編集イベントを購読する処理、次回実行時に現在位置を比較する処理もない。従って、現時点で手動オフセットが保持・再適用される機能はない。

### 7.2 実機検証が必要な候補

目標式は次でよい。

```text
最終位置 = 現在の親文字から再計算した標準位置 + 保存済み相対オフセット
```

初回生成時に `standardX/Y` と最終 `left/top` の差を、親文字サイズまたはem基準の `offsetX/Y` に変換する案は実装候補である。本文移動だけなら絶対座標より差分を再利用しやすいと考えられるが、本文サイズ変更・変形を含む再適用は実機で確認が必要である。

ただし、現在のスクリプトにはドラッグ後に通知を受ける編集イベントや、生成時の標準位置を記録する処理がない。したがって、初期実装では次回スクリプト実行時に、メタデータの標準位置と現在のルビ位置を比較して差分を検出する方式が現実的である。差分検出時には、次を区別するUIが必要になる。

- 自動配置（`auto`）: 標準位置をそのまま採用。
- 標準位置からの差分あり（`auto_offset`）: 差分を保存して再配置。
- 完全手動（`manual`）: 自動再配置の対象外。明示的なリセットでのみ標準位置へ戻す。
- ルビ不要（`suppressed`）: 生成対象外であり、読みの空欄とは別扱い。

回転、親グループの変形、縦横組、ルビのスケール変更を考慮するため、差分を単純な文書座標のx/yだけで保存するのは避ける。少なくとも横書き／縦書きごとのem基準軸を定義し、実機で `left/top`, `width/height`, `geometricBounds`, 親グループの変形を確認する。検出できない場合は `manual` として保護し、勝手に上書きしない。

## 8. Illustrator上の文字カーソルと局所編集

### 8.1 現行コードから確定できる事実

現行コードは `activeDocument.selection` から `TextFrame` を取り出し、`textFrame.contents` と `textRange.characters` を処理する。しかし、文字カーソル位置、選択文字列、選択範囲を読み取るコードはない。従って、現在の実装がカーソル連動の局所編集を提供しているとは言えない。

### 8.2 実機検証が必要な候補

ExtendScriptからIllustratorの点滅カーソル位置を安定して取得できることは、この調査資料や現行コードからは確認できない。`document.selection` から選択文字列やテキスト範囲相当を得られるか、カーソルの文字オフセットを得られるか、ScriptUIダイアログ表示中も選択状態を扱えるかは、対象バージョンの実機検証が必要である。

現実的な段階案は次のとおりである。

1. Phase 1 は既存GUIの文字ボタン／入力欄を利用し、選択した `characterIndex` にメタデータを付ける。
2. 次に、スクリプト起動時の選択対象がテキスト範囲として取得できる環境だけを検出し、取得できた範囲を局所編集の初期範囲にする。
3. APIで範囲を得られない環境では、対象フレームを選択してGUI内で前後コンテキストを検索・選択する代替UIを用意する。
4. 近傍探索で複数候補が出た場合は、選択肢を表示し、無条件に更新しない。

つまり、「カーソル連動」は拡張機能として実験し、「選択範囲またはGUI指定による局所編集」を互換性のある基準機能にするのが安全である。

## 9. 辞書と自動読み生成

### 9.1 辞書層

仕様の優先順位（文書内明示指定 > 案件辞書 > 共通辞書 > 自動候補 > 要確認）は、データモデルの解決段階として実装する。辞書レコードは最低限、表記、読み、方針、出典／メモ、適用範囲、更新日時を持つ。文書内例外は辞書を直接書き換えず、本文アンカーに紐づく override として保存する。

同じ語の修正を「この箇所だけ／この文書／この案件／共通辞書」へ昇格する操作は、候補レコードと確定レコードを分けることで安全に扱える。公開リポジトリには空のスキーマ、サンプル、テスト用の非実在データだけを置き、実案件辞書は置かない。

### 9.2 読み生成方式の比較

| 方式 | 長所 | 短所 | Mac/Windows・オフライン評価 |
|---|---|---|---|
| ExtendScript単体の規則 | 配布が `.jsx` 一つで済む。外部プロセス不要。 | 日本語の形態素解析、固有名詞、熟字訓、文脈依存読みが弱い。誤読を見抜きにくい。 | 最も容易だが、総ルビの品質を満たす方式ではない。補助的な文字分類・既知語処理に限定。 |
| 辞書ファイルのみ | 固有名詞・展示用語を確実に上書きできる。オフラインで再現可能。 | 未登録の一般語、活用、分かち書きは別途処理が必要。辞書配布・文字コード・更新規約が必要。 | 現行環境との統合が容易。案件辞書／共通辞書の第一段階に適する。 |
| Sudachi / MeCab + UniDic等 | 分かち書き・品詞・読み候補の品質と拡張性が高い。 | ランタイム・辞書サイズ・ライセンス・Mac/Windows配布、プロセス起動、バージョン固定が必要。ExtendScript単体では扱いにくい。 | オフライン化は可能だが、利用者への導入負担が大きい。別ツール／事前処理に分離すべき。 |
| 外部サービス／クラウド | 導入が軽い場合がある。 | ネットワーク・機密原稿・再現性・サービス依存。 | 展示原稿とオフライン要件に反するため非推奨。 |

### 推奨

Phase 1では自動読み生成を実装しない。Phase 2で共通辞書、案件辞書、文書内例外を導入し、Phase 3で解析エンジンを比較検証する。総ルビの候補生成は「自動確定」ではなく、読み・出所・要確認フラグをGUIへ渡すインターフェースにする。

最終的には、ExtendScriptをUI・文書操作・配置に集中させ、SudachiまたはMeCab系処理はオフラインの補助コマンド／アプリとして分離する案が品質面では最も有望である。ただし、Mac/Windows双方へ配布する段階ではランタイム同梱または事前生成ファイルの仕様が必要になる。導入容易性を優先する初期運用では辞書方式を先に採用し、解析器は任意の候補生成器として後から差し替え可能にする。

ルビの基本フォントは仕様どおりUD教科書体を想定したプリセットにできるが、フォント名の存在チェックで処理を必須化しない。見つからない場合は親文字フォントまたはユーザー設定へフォールバックし、使用フォントをメタデータに記録する。

## 10. 単一 `.jsx` と段階的分割

| 案 | 利点 | 欠点 |
|---|---|---|
| 単一 `.jsx` を維持 | 現行の配布・実行手順を変えない。ExtendScriptの古い互換性を保ちやすい。差分が小さく、既存挙動を守りやすい。 | GUI、データモデル、配置、保存が肥大化し、テストが難しくなる。 | Phase 1〜初期Phase 2に推奨。 |
| 複数ファイルへ一括分割 | 責務ごとの見通し、再利用、単体テスト性が改善する。 | ExtendScriptの読み込み方法、相対パス、配布漏れ、古いAI互換性の問題が増える。 | 早すぎる分割は避ける。 |
| 段階的分割 | 実行入口を維持しつつ、純粋関数・データモデルから切り出せる。 | 移行期間に二重実装や境界の不整合が発生する。 | 最終的な推奨。 |

分割する場合も、最初はファイルを増やすのではなく、現行 `.jsx` 内で次の関数境界を確定するのがよい。

```text
readRubyRecords() / writeRubyRecords()
resolveBaseAnchor()
buildRubyPlan()
computeStandardPlacement()
applyRubyPlan()
```

`placeOneRuby()` の既存計算を直ちに書き換えず、Phase 1ではその呼び出し前後に状態の読込・記録を置く。後で純粋な計画生成部分を別ファイルへ移せる。

## 11. 主要リスクと検証が必要な事項

### 11.1 現行コードまたは仕様から確定できる事項

- 現行の対応方針は macOS / Windows と ExtendScript対応Illustratorである（`requirements.md`）。
- 現行コードは `TextFrame`、`contents`、`textRange.characters`、`left/top`、`geometricBounds` 等を使用している。
- 既存コードには、バージョン判定、機能検出、`name`／`note` の永続化、固有IDの保存、選択範囲の保存、手動オフセットの再適用はない。
- `createOutline()` はフレーム単位で一時生成し、処理後に削除する実装である。これは現行コードで確認できるが、全環境で同じ性能・精度になることまでは示さない。

### 11.2 Illustrator実機で検証が必要な仮説・候補

| 項目 | 未確定の内容 |
|---|---|
| `name` / `note` | 読み書き可能なプロパティとしての実在・最大長・Unicode、AIを閉じて再開した後の保持、複製・コピー・グループ化時の保持。 |
| 固有ID／安定識別子 | `uuid` 等の利用可能性、バージョン差、保存・複製・別文書へのコピー時の安定性。`frame.name` は安定性を確認していない。 |
| TextRange／カーソル／選択範囲 | `document.selection` から得られる型、選択文字列・TextRange・カーソルの文字オフセット、ScriptUI表示中の挙動。 |
| 手動オフセット | ドラッグ後の位置を取得できるか、標準位置との差を検出できるか、次回に相対値として再適用できるか。現行コードは未対応。 |
| 回転・拡大縮小 | `left/top`、`geometricBounds`、`width/height` と親グループの変形の関係。文書座標、ローカル座標、em基準のどれが再配置に適するか。 |
| バージョン互換性 | 対象とするIllustrator CS／現行版のDOMプロパティ、ScriptUIイベント、縦書き、エリア文字、フォント混在、`createOutline()` の挙動の共通部分。 |

ここで挙げた候補を実装上の事実として扱わず、Phase 1冒頭の小さな実機検証で確認する。

- `PageItem.note` の最大長、Unicode、複製・保存・別AIへのコピー時の保持。
- `name` と `note` がロック済み・非表示・グループ化済みオブジェクトでも読めるか。
- 対象とするIllustrator CS／現行版でのフレーム固有IDの有無と安定性。
- `document.selection` から選択文字列／テキスト範囲／カーソル位置を取得できる実際の差異。
- 縦書き、エリア文字、ポイント文字、混在フォント、合字、異体字、空白・改行を含むアンカー再解決。
- ルビの移動、グループ変形、回転後に標準位置との差をどの座標系で測るか。
- 再実行時に既存のRuby生成物をどう更新・削除・保護するか。手動で編集された生成物を誤削除しない仕組みが必要。
- 大量の総ルビでの `duplicate()` / `createOutline()` の処理時間と一時メモリ。
- 過去版Illustrator、macOS、Windows間でScriptUIイベントとTextFrame DOMが同じように動くか。

上記はコードだけでは確定できない。実機の小さなテストAIを用意し、変更を本番文書へ適用せず確認する必要がある。

## 12. Phase 1 推奨最小単位

最初に実装する範囲は、既存ルビ生成を変えずに「1件のルビのメタデータ保存・再読込・本文候補の一意な再解決」を確認することに限定する。`name + note` の正式採用も、この実験結果の後に決める。

推奨する順序は次のとおりである。

1. 既存ルビ生成処理は変更しない。
2. テスト用の1件のルビについてメタデータを書き込む。
3. 保存したAIファイルを閉じて再度開く。
4. メタデータを再読込できることを確認する。
5. 保存した本文アンカーから対応する本文候補を再解決する。
6. 一意に解決できない場合は勝手に更新せず「要確認」とする。
7. ここまで確認できてから、複数ルビや `suppressed` 等へ拡張する。

この最小実験では、対象ルビに `schema`、`recordId`、本文文字列、位置、前後コンテキスト、読み、状態を記録する。`auto_offset` の検出・再適用、回転・拡大縮小、カーソル連動、自動読み生成は後続の検証・実装とする。UD教科書体はプリセットの既定値候補にするが、フォントがない環境でも処理できるフォールバックを持つ。

この段階では総ルビ、自動読み、辞書昇格、カーソル連動、本文変更後の自動再配置を実装しない。まず「既存ルビの見た目を変えず、保存・読込・曖昧時の停止ができる」ことを確認する。これができれば、Phase 2以降の辞書・解析・局所編集を既存配置ロジックの上に安全に載せられる。

## 13. 未確定事項

Phase 0 の資料からは、次を最終決定できない。

- 対応Illustratorバージョンの下限と、`note`／固有ID／選択範囲APIの共通部分。
- 文書内メタデータをグループ単位で持つか、ルビ単位で持つか。`note` 保持の実機結果で決める。
- 既存の無印 `Ruby` グループを、将来の新管理方式がどこまで認識するか。
- 本文変更で同一アンカーが複数候補になった場合の確認UI。
- 位置差分の座標変換（回転・変形を含む）と、手動ドラッグを何時点で確定扱いにするか。
- Sudachi／MeCab系の採用、辞書ライセンス、ランタイム配布方法。
- ルビ生成物をユーザーが直接編集した場合の保護方針と、再配置時の競合解決。

これらは Phase 1 の保存・読込プロトタイプと、最小の横書き／縦書きテストAIを作った後に判断するのが妥当である。
