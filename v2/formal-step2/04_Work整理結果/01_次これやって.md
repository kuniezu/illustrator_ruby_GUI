## blocker A: `FormalMultiNativeRenderer.createSpecs()` が per-item hidden を依然 `native-render-plan-incomplete` として拒否する

現在 `native-renderer.js` はtop-level `plan.status === "complete"` を確認した後、各 result について

```js
if (result.status !== "complete") fail("native-render-plan-incomplete");
```

としている。

前修正後の mixed plan は

- top-level: `complete`
- visible sibling: `complete` + segmentsあり
- overset sibling: `hidden` + `hidden-confirmed` + segments=[]

となるため、`FormalMultiRenderer.plan()` を通過しても `FormalMultiNativeRenderer.createSpecs()` で hidden result に到達した瞬間throwする。

production `persistence-adapter.jsx` は実際に

`FormalMultiNativeRenderer.createSpecs(bundle,{status:plan.status,results:plan.plans},...)`

を呼ぶため、これは実機route上のblocker。

### 修正契約

- per-item `hidden + hidden-confirmed + decision.segments=[]` は native spec生成上の **valid no-output** としてskipする。
- per-item `unresolved` / `failed` は、top-level completeと矛盾する入力として引き続きfail-closedでよい。
- 単に `status !== complete` を全許可へ緩めない。
- hiddenなのにsegments非空、outcome不正、reason不整合などcontract違反はfailする。
- suppressed complete / empty segmentsとは別概念として保持する。

## status algebra propagation audit（上流・下流・横方向）

今回の原因を1ファイル修正で終わらせず、次のsemantic tableをproduction consumer全体で確認する。

| item status | 意味 | aggregate blocker | native output | durable occurrence evidence |
| --- | --- | --- | --- | --- |
| `complete` | renderable /正常処理 | no | segmentsがあればyes | complete |
| `hidden` + `hidden-confirmed` | authoritativeにsource oversetで不可視 | no | no | hidden + source-overset-hidden |
| `unresolved` | user/evidence不足 | yes | no | unresolved |
| `failed` | 処理失敗 | yes | no | failed |
| suppressed complete | user suppression等のnormal no-output | no | no | suppressed/pending contractを既存どおり維持 |

- fully-after-visibleEndだけ hidden-confirmed になること。
- source resizeでvisibleへ戻ったとき stale hidden statusをplanning inputとして固定しないこと。
