## blocker A: durable `renderStatus="pending"` がUIで依然 `[ready]` に見える

現行 `workflow.js`:

```js
function renderStatus(occurrence) {
    return occurrence.renderStatus && occurrence.renderStatus!=="pending"
        ? occurrence.renderStatus
        : null;
}
```

現行 `Formal Multi Step2.jsx`:

```js
function statusText(occurrence) {
    var render=FormalMultiWorkflow.renderStatus(occurrence);
    if (occurrence.unsupported) return "unsupported";
    if (render && render!=="complete") return "render-" + render + ...;
    return FormalMultiWorkflow.occurrenceStatus(occurrence);
}
```

従って、reading confirmed + durable `renderStatus="pending"` のoccurrenceは `renderStatus()` がnullを返し、`occurrenceStatus()` の `ready` へfallbackする。

これは前dispatchで懸念した同型semantic bugそのもの。

### 問題

- `input ready` と `render pending` がUIで再び同一視される。
- aggregate noncomplete時にplanner-complete siblingを正しくpendingへ落としても、ユーザーにはreadyに見える。
- reopen後もpersisted pending evidenceがUIで隠れる。
- completion reportの「durable pendingをreadyへfallbackしないことを確認」はproductionコードと不一致。
- 現在の `tests/ui.cjs` は `FormalMultiWorkflow.renderStatus(occurrence)` の文字列存在を確認するstatic check中心で、実際にpending occurrenceをstatusText相当へ通していないため、この回帰を検出していない。

### repair contract

layerを明示的に分ける。

- input state: unresolved / ready / suppressed / unsupported
- durable render evidence: pending / unresolved / failed / hidden / complete
- durable `pending` が存在する場合、UIはinput readyへfallbackしてはいけない。
- `complete` はterminal native success evidenceとして扱い、必要ならinput readiness表示と区別する。
- hidden / unresolved / failedは既存どおりrender evidence優先。
- UI文言の大改造は不要。truthfulnessだけ最小修正する。

`FormalMultiWorkflow.renderStatus()`を変えるか`statusText()`側でraw `occurrence.renderStatus`を扱うかは、既存consumerを確認して副作用の小さい方を選ぶ。

### executable regression

static source matchだけでなく、少なくともpure/VM-equivalent function testで:

1. reading confirmed + render pending → `render-pending` 相当、`ready` ではない。
2. reading confirmed + render unresolved → render-unresolved。
3. reading confirmed + render hidden → render-hidden。
4. terminal complete → complete semanticを壊さない。
5. reading unconfirmed + render pending → input unresolvedとの表示優先規則を明示してtest化。
6. reopen/store roundtrip後のpendingも同じ。

## blocker B: planner→durable mapping修正が `FormalMultiStore.write` のglobal monkeypatchになっている

現行generated Bridgeは `multi-store.js` 読込直後に:

```js
(function(){
  var originalWrite=FormalMultiStore.write;
  FormalMultiStore.write=function(note,value){
    var k,o;
    if(value&&value.renderStatus!=="complete"&&value.occurrences)
      for(k=0;k<value.occurrences.length;k++){
        o=value.occurrences[k];
        if(o.renderStatus==="complete")o.renderStatus="pending";
      }
    return originalWrite(note,value);
  };
}());
```

を入れている。

これは今回欲しい「aggregate noncomplete failure bundle内のplanner-complete siblingだけpendingへmappingする」責務より広い。

### 問題

- persistence boundaryの局所規則をstore serializer全体へ横展開している。
- noncomplete bundleを書き込む別routeまで暗黙にoccurrence statusを書き換える。
- `write()`が入力valueをmutationするため、serialize前後でcaller objectの意味が変わる。
- future routeで「noncomplete top-level + occurrence complete」が正当な証拠になる場合も無条件で消す。
- status意味論のconsumer境界問題を、global normalizationで隠す形になっている。

### repair direction

**このglobal monkeypatchは撤去し、plan noncomplete failure bundleを構築する場所で明示的mappingする。**

現在のfailure mapping loopで、matching plan itemについて例えば:

- `unresolved` → unresolved
- `failed` → failed
- valid hidden-confirmed → hidden
- planner `complete` → durable pending
- suppressed/no-output →既存semanticに沿ってpending/suppressed扱い

と局所的に書く。

storeはserialize/deserializeの責務に戻し、planner/render semanticを知らない状態を維持する。

terminal success / lifecycle failureの `terminalBundleNote()` は別契約なので、今回のfailure mapping helperを無理に共通化しない。

### regression

1. generated plan noncomplete: planner-complete sibling → pending。
2. `FormalMultiStore.write()`単体は入力bundleのrenderStatusを勝手にmutationしない。
3. unrelated noncomplete bundle serializeでoccurrence completeを書き換えないこと（schema上許容されるならroundtrip保持。schema上不許容ならvalidatorの責務として明示）。
4. hidden/unresolved/failed evidence lossless。
5. terminal success routeはvisible eligible completeを保持。
