## blocker A: `FormalMultiRenderer.plan()` の first-blocker early return が全体状態を隠す

現在 `multi-renderer.js` はoccurrenceを順にplanし、

```js
if (result.status !== "complete" && result.status !== "hidden")
    return { status: result.status, plans: plans };
```

で最初の unresolved / failed に到達した時点で終了する。

これは今回の実機で実際に露呈した。

1. 最初のsaveでは `occurrence-4|unresolved|split-hint-required` だけが見えた。
2. それを解消した次のsaveで、後方にあった `occurrence-9|hidden|source-overset-hidden` が初めて見えた。

つまり planner は一度に全occurrenceを評価できるのに、renderer aggregate層がfirst-blockerで情報を切っていた。

### 問題

- 後続occurrenceの hidden / unresolved / failed evidenceが同じsaveでdurableにならない。
- unresolvedを1件直すたびに次の問題が出る「モグラ叩き」になる。
- 先にunresolved、後ろにfailedがある場合、top-level statusが `unresolved` のままになり、`FormalMultiOrchestration.planAll()` の **failed > unresolved > complete** precedenceと矛盾する。
- failure persistenceはprefix分のplansしか持てず、後続occurrenceをpendingへ戻すため、現在attemptで既に判定可能な情報を捨てる。
- item status / aggregate statusを明文化した直後なのに、aggregate consumerが全itemを見ずに結果を確定している。

### repair contract

`FormalMultiRenderer.plan()` は **全managed occurrenceを最後までplanしてからaggregate** する。

- per-item `complete`: non-blocking
- confirmed `hidden`: non-blocking
- `unresolved`: aggregate unresolved
- `failed`: aggregate failed
- aggregate precedenceは `failed > unresolved > complete`
- suppressed/no-outputは既存semanticを維持
- planning中はDOM mutationしないので、全item評価してもrenderer safetyは緩まない
- `render()` はaggregate completeでない限り従来どおり `adapter.reconcile()` を一件も呼ばない

`FormalMultiOrchestration.planAll()` と `FormalMultiRenderer.plan()` のaggregate semanticsを同じ表で照合すること。無理な共通helper化は不要だが、意味は一致させる。

### failure persistence

production generated BridgeTalkのnoncomplete pathも合わせて確認する。

現在 `failurePlan = plan.plans[plan.plans.length-1]` 前提があるため、full-pass planningへ変更すると「最後のitemがblocker」とは限らない。

- durable failure bundleは **全plan item** のstatus/reason/boundary evidenceをoccurrenceへ反映する。
- callback/debugの代表reasonが必要なら、実際のblockerからdeterministically選ぶ（failed優先、次にunresolved等）。last-itemを暗黙採用しない。
- persisted noteをpalette authorityとする既存契約は維持。
- split boundary evidenceを全 unresolved occurrenceについて同一saveで保持できること。

### executable regression

最低限:

1. unresolved A + complete B + hidden C → plans 3件すべて保持、aggregate unresolved、renderer mutation 0。
2. unresolved A + failed B → aggregate failed（orderingを逆にしてもfailed）。
3. hidden A + unresolved B + hidden C →全item evidence保持、aggregate unresolved。
4. 複数 split-hint-required occurrence → 1 saveで各occurrenceのboundary evidenceがdurable。
5. first blocker解消後に「以前評価可能だった後続状態が初めて出る」回帰を禁止。
6. aggregate complete時だけnativeへ進む既存安全契約を維持。

## blocker B: BridgeTalk `send() === false` がpendingのまま終端しない

`persistence-adapter.jsx` の `bridge()` / `renderedBridge()` は現在、

```js
sent = bt.send();
callbacks.pending(sent === false ? "... send=false ..." : "... send=true");
return bt;
```

となっている。

`send=false` でもfailure/successへ収束せず、callbackが来なければUIは `savePending=true` のまま残る。shared checklist A6 は `timeout / send(false) / result / error / callback lifetime` を明示的に確認対象としているが、現行 `tests/persistence-adapter.cjs` はtimeout/onErrorは実行確認している一方、send=falseのterminal transitionを実行確認していない。

### repair contract

まず既存BridgeTalk precedent/契約を確認し、`send() === false` の意味に沿って処理すること。ただしどの解釈でも **pendingのまま永久待機は不可**。

- falseが「送信されていない」と保証されるなら、source unchangedを前提に明示的send-failureへterminal遷移し、retrySafe可否を契約化する。
- falseでもhost execution可能性を排除できない契約なら、`transport-uncertain` としてclose/reopen resyncを要求する。
- `activeMessages` にstale messageを残さない。
- pending callbackを出した後にterminal callbackを同期発火するようなUI raceを作らない。false時のcallback順序を明示する。
- simple `bridge()` と practical `renderedBridge()` の両方を確認する。

### executable regression

FakeBridgeで `send() => false` を実行し、

- pending-onlyで終わらない
- active message leakがない
- UI-equivalent stateがsave/close不能の永久pendingにならない
- retrySafe / transport classificationが契約どおり

を確認する。
