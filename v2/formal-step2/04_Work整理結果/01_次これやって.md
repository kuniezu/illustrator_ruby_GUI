## blocker A: noncomplete aggregateで「plan complete sibling」をdurable `renderStatus=complete` にしている

generated `persistence-adapter.jsx` のplan noncomplete pathは、いったん全occurrenceをpendingへ正規化した後、全plan itemについて

```js
failureBundle.occurrences[j].renderStatus = plan.plans[i].status;
```

としている。

full-pass planning後、例えば

- A = unresolved (`split-hint-required`)
- B = complete（geometry/segmentsはplan可能）
- C = hidden-confirmed

ならaggregateは unresolved でnative transactionは開始しない。

しかし durable bundle は現在

- A renderStatus=unresolved
- B renderStatus=complete
- C renderStatus=hidden

になる。

Bは「planner complete」であって「native render terminal success」ではない。aggregate noncompleteなので今回attemptではnative renderされていない。first-blocker時代にも先行complete itemで潜在していたが、full-pass化で全後続complete itemへ広がった。

### repair contract

planner item statusとoccurrence durable render evidenceを分離する。

aggregate noncomplete時:

- item `unresolved` → occurrence `renderStatus=unresolved` + reasons/boundaries保持
- item `failed` → occurrence `renderStatus=failed` + reasons保持
- item confirmed `hidden` → occurrence `renderStatus=hidden` + `source-overset-hidden`（no-output authoritative evidence）
- item `complete` → **今回render未実行なので新規に`complete`へ昇格させない**
  - 原則 pendingへ正規化する。
  - 既存terminal complete evidenceを条件付きで保持したい場合は、current render inputsとactive native ownershipが同一であることを明示的に証明する契約が必要。推測保持は禁止。最小修正ではpendingが安全。
- suppressed/logical-only/unsupportedは既存contractどおりpending/suppressed semanticsを維持。

terminal `renderStatus=complete` はnative lifecycle成功後の `terminalBundleNote(..., true, ...)` だけが与える、という境界を明文化する。

### executable regression

1. unresolved A + planner-complete B → aggregate unresolved、B durable renderStatusはcompleteにならない。
2. failed A + planner-complete B → aggregate failed、B durable renderStatusはcompleteにならない。
3. unresolved A + hidden C → A unresolved、C hiddenは保持。
4. multiple unresolved + complete siblings →全boundary/reason保持、complete siblings pending。
5. aggregate complete → native success後だけeligible visible occurrencesがcompleteになる。
6. reopen roundtrip後も同じ。

## blocker B: BridgeTalk callbackがplan failureを常に `renderStatus="unresolved"` と報告する

`renderedBridge()` の `B-render-persist:render-failed:plan` parseでは現在、

```js
renderStatus: parts[0] === "plan" ? "unresolved" : "failed"
```

となっている。

一方generated bodyはaggregate `plan.status === "failed"` のとき durable bundleを `renderStatus="failed"` で保存する。

したがって、source note authorityはfailedなのにcallback valueはunresolvedとなり、diagnosticも `transport-success / render-unresolved` になる。

UIはpersisted noteを再読するためbundle自体は救われるが、stateText / debug / callback contractがauthorityと食い違う。

### repair contract

- callback `renderStatus` はauthoritative persisted FormalMulti bundleのtop-level `renderStatus` と一致させる。
- wire payloadにaggregate statusを明示追加するか、persisted noteをdecode後にFormalMultiStore.readして導出する。
- plan failed / plan unresolvedを区別する。
- diagnosticsも `render-failed` と `render-unresolved` を区別する。
- persisted note readback authorityは維持。
- representative blockerはdebug用でありtop-level statusのsource of truthにしない。

### regression

- aggregate failed → callback renderStatus failed / persisted bundle failed / diagnostics failed。
- aggregate unresolved → callback unresolved / persisted unresolved。
- callbackとpersisted top-level status不一致を禁止。

## audit C: user-observed duplicate `B-render-persist: send=true` diagnostic

実機ログで1 saveにつき `B-render-persist: send=true` が2回見えていた。

actual flowを追うと二重送信ではなく、

1. pending callbackでdiagnostics `[send=true]` をUIへ表示
2. success callbackで `value.diagnostics = diagnostics.concat([terminal message])`
3. UIがvalue.diagnostics全体を再度append

するため、同じpending diagnosticをterminal callback時に再表示している。

これはnative二重実行ではないが、runtime診断を紛らわしくし、今後real duplicate sendを見分けにくい。

### repair contract

- 1 save / 1 BridgeTalk sendにつき `send=true` diagnosticはUI consoleへ1回だけ表示。
- terminal callbackは新規terminal diagnosticだけをappendするか、UI側で重複しないsequence contractにする。
- timeout/error/send=falseでも同様に既出pending diagnosticを重複表示しない。
- actual send回数・callback回数のguardは変更しない。

### regression

UI-equivalent diagnostic sequenceで

`send=true → terminal success/unresolved/failed`

が各1回だけ現れること。これは二重send testとは分ける。
