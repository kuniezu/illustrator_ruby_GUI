## blocker: `setRetryBlocked(true)` が `setSavePending(false)` を通じて editor/list を再有効化する

現在:

```js
function setRetryBlocked(value) {
    retryBlocked = !!value;
    transportUncertain = retryBlocked;
    setSavePending(false);
    closeButton.enabled = true;
}
```

`setSavePending(false)` は

- `list.enabled = true`
- `readingInput.enabled = true`
- `enabledCheck.enabled = true`
- `confirmedCheck.enabled = true`

に戻す。

そのため blocked stateは

- save: disabled
- split/merge/review: disabled
- close: enabled
- **list/editor: enabled**

になっている。

これは前dispatchの契約「blocked中はsave/edit/list/actionを固定し、closeだけをsafe escapeとして許す」と矛盾する。

### 修正要件

- pendingとblockedを別状態としてcontrol enablementを一意に管理する。
- pending中: save/close/list/editor/actionsすべてdisabled。
- blocked中: closeのみenabled。save/list/editor/split/merge/review/suppress/re-enableはdisabled。
- normal中: retryBlocked falseかつsavePending falseのときだけ通常controlを有効化。
- blocked中にlist selection changeやreading editでbundle/revisionが変化しないこと。
- blocked中にsame paletteからsave callbackを再発火できないこと。
- close/reopen後、新paletteでpersisted recovery/resyncを経てnormalへ戻る既存契約を維持する。
- requestId / bundle.revision callback race guardを維持する。

## executable regression

static文字列確認だけでなくUI-equivalent state transitionを実行してassertする。

1. normal → pending: save/close/list/editor/actions disabled。
2. pending → blocked: closeのみenabled。
3. blockedでreading/list操作不能、revision不変。
4. blockedでsave再発火不能。
5. blocked → close/reopen → recovery convergence → normal/save可能。
6. ordinary retry-safe failureならnormalへ戻れる。
7. callback race guard維持。
