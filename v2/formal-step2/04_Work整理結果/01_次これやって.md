## blocker A: production recovery wrapperを実行する回帰がない

現在の `tests/terminal-recovery-state-machine.cjs` は

- `FormalAreaTextNativeRecovery.converge()`
- `FormalAreaTextNative` のpure state transitions

を直接実行している。

一方、実際のgenerated BridgeTalk bodyでは、

1. `FormalAreaTextNativeRecovery.converge(...)`
2. step callback内で旧 `recoverNative(note)` を呼ぶ
3. `recoverNative()` がその時点のdurable manifestを再readし、`restart()`をもう一度行って1 action実行する
4. source noteを更新
5. step callbackがmanifestを再readしてconvergeへ返す

というwrapper固有の経路を通る。

`tests/persistence-adapter.cjs`は現在、この経路について `FormalAreaTextNativeRecovery.converge` / `native.recovery` / `terminal|steps=` の文字列存在を確認するstatic assertionのみで、実際のgenerated helperを走らせていない。

そのため、pure desired state machineが正しくても、wrapper側で note / action / durable state の対応がずれた場合を捕捉できない。

### 3. deterministic recovery failure classificationを実経路で確認

現在 `converge()` / duplicate / no-progress / loop-limit等がgenerated bodyでthrowすると、BridgeTalk `onError`へ落ちてhost側では `transport-uncertain` になる可能性がある。

安全側でblind retryを止める点は正しいが、reportの「deterministic recovery failureはtransport uncertaintyと区別」という記述と実経路が一致するかを確認する。

- source/note mutation後でauthoritative noteなしならuncertain扱いを維持してよい。
- mutation前・またはauthoritative noteを返せるdeterministic recovery failureを構造化できるなら区別する。
- 無理に分類を増やして安全性を下げない。
- 少なくとも02の報告と実装の意味を一致させる。
