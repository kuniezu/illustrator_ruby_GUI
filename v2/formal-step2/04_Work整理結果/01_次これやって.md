## blocker A: `mergeAdjacentWithPlan()` が single-occurrence test 前提になっている

現行 `occurrences.js`:

```js
function mergeAdjacentWithPlan(bundle, occurrenceIds, plan) {
    var candidate, projected, expectedId;
    if(!plan || plan.status!=="complete" || !plan.results || plan.results.length!==1 ||
       plan.results[0].status!=="complete" ||
       !plan.results[0].decision || plan.results[0].decision.status!=="complete")
        fail("merge-current-plan-not-complete");

    candidate=FormalMulti.replaceOccurrences(bundle, mergeAdjacentCandidate(bundle, occurrenceIds).occurrences);
    projected=FormalMultiProjection.project(candidate);
    expectedId=FormalMultiProjection.id(projected, projected.occurrences[0]);
    if(plan.results[0].annotationId!==expectedId)
        fail("merge-current-plan-identity-mismatch");
    return candidate;
}
```

しかしproduction `FormalMultiOrchestration.planAll()` は projected bundle の **全annotation** を `results` に積む。

実機fixtureは12 occurrenceあり、confirmed/renderable siblingが複数存在する。従って guarded merged target がcurrent geometryでcompleteでも:

- `plan.results.length !== 1` になり得る。
- target merged occurrenceがbundle先頭でなければ `projected.occurrences[0]` は別occurrence。
- `plan.results[0]` もtarget annotationとは限らない。

この場合 geometry expand でmerge可能になったはずのguarded targetが、multi fixtureでは常に `merge-current-plan-not-complete` / identity mismatchで拒否され得る。

現在の追加test `current complete observation permits a guarded merge while current split evidence rejects it` は `甲乙` 1 occurrenceだけのfixtureなので、このproduction multi-item failureを検出できない。

### repair contract A

- merged target occurrence / projected annotation IDを明示的に特定する。
- aggregate `plan.status === complete` は必要条件として使ってよいが、`plan.results.length===1` を要求しない。
- `plan.results` から **target annotationIdに一致するitem** を探し、そのitemが `status=complete` かつ `decision.status=complete` であることを確認する。
- targetがmissing / duplicate / unresolved / failed / hiddenなど、merged visible candidateのcomplete証明にならない場合はfail-closed。
- siblingのcomplete/hidden/suppressedはtarget判定と混同しない。
- `projected.occurrences[0]` の位置依存は禁止。merge対象のoccurrenceId/annotationIdからtarget identityを計算する。

### executable regressions A

最低限:

1. production-like 10+ occurrence fixtureで、guarded merge targetが中間index（例 occurrence-4）にある。
2. confirmed visible siblingが複数あり `plan.results.length > 1`。
3. target merged candidateがcurrent observationでcomplete → merge許可。
4. sibling hidden/suppressed coexistenceでもtarget completeなら許可。
5. target unresolved/failed → reject。
6. aggregate completeでもtarget result missing/duplicate → reject。
7. target identityを先頭itemと取り違えない。

## blocker B: merge拒否前に `saveEditor()` がbundle/revisionをmutateする

前STATE-24修正では、known blockerのmerge拒否を `saveEditor()` より前に行い、reject時のbundle/revision/selection不変を保証していた。

現行UIは:

```js
first=bundle.occurrences[currentIndex];
second=bundle.occurrences[currentIndex+1];
saveEditor();
first=bundle.occurrences[currentIndex];
second=bundle.occurrences[currentIndex+1];
...
if(wouldRestoreSplitBlocker(...)) {
    currentPlan=currentMergePlan(first,second);
    ...
}
```

`saveEditor()` は no-opであっても `editRevision++` / `bundle.revision=editRevision` を行う。reading/enabledのeditor内容が変わっていればbundle自体も更新する。

従って current observation unavailable / still split-required / target plan reject の場合でも、merge操作だけでbundle/revisionが変更される。

前dispatch reportの:

> merge拒否はcurrent plan未証明時にbundle/revision/selectionを変えず

は現productionコードと一致しない。

### repair contract B

mergeはtransactionalに扱う。

- current editor contentsを評価へ反映する必要があるなら、**temporary candidate bundle** に適用してcurrent planを作る。
- guard revalidation成功 + merge許可が確定するまではlive `bundle` / `editRevision` / selection / source note / native generationをmutateしない。
- reject時はUI editor text自体を勝手に巻き戻す必要はないが、domain bundle/revisionはmergeクリック前と同一に保つ。
- allow時のみeditor commit + merge commitを一貫したrevision policyで反映する。
- no-op `saveEditor()` revision increment問題をこのrouteだけglobal redesignしない。merge decisionのatomicityを最小修正する。

### executable regressions B

1. guarded merge + observation unavailable → reject、bundle JSON/revision/current occurrence identity不変。
2. guarded merge + still split-required → reject、bundle/revision不変。
3. editor readingに未保存変更あり + reject → live bundleには未反映（UI fieldはそのままでよい）。
4. guarded merge complete proof → allow時だけeditor内容とmergeがcommitされる。
5. reject後に通常save可能。
6. rejected mergeはsource note/native transitionを開始しない。
