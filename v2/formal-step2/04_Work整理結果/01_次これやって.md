## blocker A: mergeが既知のsplit blockerを復活させる

現行UIでは、split-hint-requiredを解消するために局所分割したchildrenを、そのまま隣接結合できる。

結果:

1. parent `再編集` が `split-hint-required`。
2. `再｜編集` に分割。
3. children readingを再確認。
4. 隣接結合。
5. merged surfaceが再び `再編集`。
6. render boundary evidenceは消える。
7. 次回保存で同じ `split-hint-required` が復活。

### repair contract

まずproduction semanticsを確認し、次のどちらかでfail-closedにする。

推奨順:

1. **既知のline-crossingを復活させるmergeをUI/modelで拒否する。**
   - merge対象がsplit lineage由来で、元のsplit境界を跨いで再結合すると同じplanner blockerを復活させる場合は `merge-would-restore-split-blocker` 等で明示的に拒否。
   - ユーザーには「この結合は再び行境界をまたぐため結合できません」相当を表示。
2. もし既存契約上merge自体を許す必要があるなら、merge後にsplit boundaryを失わず、plannerが同じ無限往復にならない明示的semanticを設計する。

**単にplannerを緩めてsplitを不要扱いにしてはいけない。**


### audit / repair contract

- split child / merged result / reopen後 / split-again でID衝突や誤解釈が起きないこと。
- lineageはsource historyとして使い、display/debug用のIDと混同しないこと。
- merged IDを新規生成するかroot identityへ戻すかは、既存 persistence/native logicalSegmentId 契約を確認して最小変更を選ぶ。
- 既存native physical ownershipを壊すID再利用は禁止。
- split→merge→splitで同じIDが重複生成されないこと。

## horizontal audit: 今回のcycleだけ一巡する

今回のblocker修正後、以下をまとめて確認する。

### split / merge model

- split child readingは再確認必須のまま。
- merge後readingConfirmed=false契約が妥当か。
- merge後renderStatus=pending。
- stale renderBoundaries / unresolvedBoundariesは残らない。
- lineageが重複・循環・爆発しない。
- split→merge→splitでvalid bundleを維持。

### UI / review queue

- merge拒否時にbundle/revision/current selectionを変更しない。
- stateTextへ明示理由を出す。
- reviewQueueがsplit children / merged itemを二重計上しない。
- merge後にpending/unresolvedがreadyへ誤表示されない。
- list refreshでselection/currentIndexが壊れない。

### persistence / reopen

- split stateを保存→reopenして同じchildren identity/lineage/evidence。
- rejected mergeはsource noteを変えない。
- valid mergeが存在する場合は保存→reopenでsemantic equivalence。
- no-op saveでsplit boundary evidenceを破壊しない。

### planner / renderer

- split-hint-requiredは本当に必要なline crossingだけで発生。
- valid split childrenはplanner completeへ進める。
- hidden/suppressed siblingはmerge guard判定に混入しない。
- aggregate failed/unresolved precedenceは維持。

### native lifecycle

- splitによりlogical segment setが変わった場合のtransition/retirementが正しい。
- rejected mergeではnative generation/retirementを開始しない。
- split→render→再編集でold physical outputが重複しない。
- source/unmanaged objectをretireしない。
