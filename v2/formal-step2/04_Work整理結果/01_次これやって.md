## blocker A: post-activation failure後の「同じpalette retry」はまだ成立しない

current practical pathはpost-activation retire/cleanup/finish failure時にauthoritative noteをpaletteへ返すようになったが、native manifest自体は`operation.phase="activated"`や`retirementQueue` / `cleanupQueue`を保持し得る。

`FormalAreaTextNative.beginOperation()` は既存operationがありrequestIdが新しい場合 `operation-already-active` を投げる。

したがって、post-activation failure後にcachedNoteだけ同期して新しいrequestIdで再保存しても、manifest recoveryを行わなければ次のnative transactionを開始できない。

repoには既に `area-text-native-recovery.js` があり、

- `prepare-candidates`
- `reverify-candidates`
- `cleanup-discarded`
- `cleanup-retirement`
- `finish-operation`

のrestart/recovery契約を持つ。しかしcurrent `Formal Multi Step2` のruntimeSources / renderedBridgeBodyはこのrecovery moduleをproduction pathへ読み込んでおらず、実用save pathから未接続のまま。

### 修正要件

- 新operationを始める前に、persisted native manifestがclean/recoverableかを確認する。
- operation / retirementQueue / cleanupQueueが残っている場合、既存`FormalAreaTextNativeRecovery`契約を優先して安全に収束させてから新requestへ進む。
- post-activation cleanup failureではrollbackしない既存契約を維持する。
- cleanup対象physical IDはsourceFrameId + physical IDで再解決し、duplicateはSTOP、missingは既存recovery契約どおりalready removedとして扱う。
- recovery完了後のmanifest noteをexact readbackし、そのnoteを次transactionのexpected note/cached authorityにする。
- reopen後も同じrecoverable manifestから収束できること。
- current practical pathで不要な独自recoveryを新造せず、既存`area-text-native-recovery.js`を接続・不足補強する方を優先する。

## blocker B: BridgeTalk timeout / onErrorは「source未変更の普通のfailure」と断定できない

`renderedBridge()`は`onTimeout` / `onError`でplain failure callbackを返し、paletteは`setSavePending(false)`して再保存可能になる。

しかしtimeoutは、Illustrator側bodyが未実行だったことを証明しない。bodyが既にsource note / native manifest / rendered outputsを変更している途中、またはtimeout後も処理が継続する可能性を保守的に扱う必要がある。

同様に`onError`も、throw位置によってはsource noteを書いた後の可能性がある。

現状ではauthoritative noteがないtransport uncertainty後にblind retryでき、

- stale cachedNote
- active prior operation
- late completionとのrace

を起こし得る。

### 修正要件

- `onTimeout` / authoritative noteを伴わない`onError`を、通常の確定failureと同じretry-safe状態にしない。
- `transport-uncertain` / `indeterminate`等の明示状態を導入してよい。
- uncertain後は、document path + UUID identityを使ったread-only resync / recoveryでsource noteとnative manifestを再取得・収束できるまで、新saveを許可しない。
- late callback / timeout後継続とのraceを考慮し、単にpalette側cachedNoteだけ読み直して終わりにしない。
- safe resyncが設計上困難なら、少なくともblind retryを禁止し、reopen/recoveryに明示的に遷移させる。ただしreopen側でもblocker Aのmanifest recoveryが機能すること。
- UIは「保存失敗」と「結果不確定」を区別する。

## blocker C: re-enable時だけframe-level renderStatusがpendingへ戻らない

`setOccurrenceEnabled()` は現在、

`if (changed && !target.enabled) ... next.renderStatus="pending"`

なので、enabled `true→false` ではframe-level statusがpendingになるが、`false→true` では変更があってもframe-level `bundle.renderStatus` をresetしない。

terminal success後にsuppressed occurrenceを再有効化すると、occurrence自体は以前のsuppression経路でpendingでも、frame-level statusが`complete`のまま残り得る。

前completion reportの「reading/confirmed/enabledのsemantic editはframe-level pendingへ戻す」という契約とも不一致。

### 修正要件

- enabledが実際に変化した場合は、disable / re-enableの両方向でframe-level renderStatusをpendingへ戻す。
- occurrence render evidenceもcurrent plan前提に合わせてclear/pendingにする。
- same-value enabled commitはno-opとしてevidenceを保持する。
- `complete → suppress → save/reopen → re-enable` を直接回帰化する。

## blocker D: verify failureでdurable abortを二重実行し得る

`FormalAreaTextNativeIntegration.verify()` のcatchは既に

- `coordinator.abort(...)`
- `error.lifecycleAborted = true`

を行ってthrowする。

しかしproduction `persistence-adapter.jsx` のouter native catchは、`!activated && seam && prepared`だけを見て再度 `seam.abort(prepared,nativeError)` を呼ぶ。

そのためverify failureでは、integration側でoperationをnullへabortした後にouter側がもう一度coordinator.abortへ進み、`operation-request-mismatch`等の二重abortを発生させ得る。

さらにhost candidate disposalとdurable abortの責務がintegration catch / outer catchに分散しており、cleanupPendingのauthoritative ownershipが曖昧。

### 修正要件

- pre-activation failureのabort / host disposal / cleanupPending durable queueを1回だけ実行する契約に整理する。
- `error.lifecycleAborted`をただ付けるだけでなくproduction outer catchが尊重する。
- verify failure時にcandidate host cleanupが必要なら、coordinator abort前後のどこで誰がdisposeするかを一意にする。
- prepare failure / verify failure / explicit outer abortの3経路で二重abort・二重disposeが起きないことを回帰化する。
- existing copy-on-writeとcleanupPending semanticsを弱めない。

## blocker E: reopen/UIはnative recovery pendingを認識していない

`Formal Multi Step2.jsx` 起動時はFormalMultiStore bundleを読むが、native manifestのoperation / retirementQueue / cleanupQueueをUI stateとして確認していない。

post-activation failure後のFormal Multi bundleはrender completeになり得る一方、native manifestはcleanup/recovery pendingのまま残り得る。

その状態でpaletteを閉じて再起動すると、一覧はrender complete相当に見え、stateTextも通常の「読み込み完了」から始まるが、次saveではnative operationが残っていて開始不能になり得る。

### 修正要件

- reopenまたは最初のsave preflightでnative manifest recovery stateを必ず確認する。
- `activated-cleanup-pending` / active operation等がある状態を通常readyとして隠さない。
- recovery可能なら自動または明示的な安全recoveryへ接続し、完了後にreadyへ戻す。
- duplicate/identity mismatch等で自動回復不可なら、何がpendingかをdiagnosticへ残してsaveを停止する。
- Formal Multi render outcomeとnative lifecycle recovery outcomeを別軸でtruthfulに扱う。

## blocker F: 新しいterminal testsが主にstatic regexで、state-machineそのものを実行していない

今回追加された`tests/persistence-adapter.cjs`のterminal checksは、generated bodyに文字列が存在することを確認するstatic assertionが中心。

これでは、今回見つかった

- active operationを残したpost-activation failure後の次request
- timeout/late completion uncertainty
- verify failure二重abort
- reopen recovery

のような「複数stepを跨ぐstate transition」は証明できない。

### 修正要件

今回のsliceではstatic assertionだけ増やして完了としない。

可能な範囲でgenerated BridgeTalk bodyまたはproduction-equivalent coordinatorを実行するintegration harnessを作り、最低限次のsequenceを状態値までassertする。

1. success → manifest clean / Formal Multi complete。
2. pre-activation verify failure → abortは1回 / operation clear / retry可能。
3. post-activation retirement failure → render active / operation activated + cleanup pending → recovery → finish → 次request開始可能。
4. close/reopen相当 → persisted noteだけから同じrecoveryを再開可能。
5. suppress successful state → re-enable → frame/occurrence pending → rerender success。
6. transport uncertainはblind retry不可。resync/recovery後だけretry可能。

既存`area-text-native-recovery.cjs`のpure testsを活用しつつ、practical persistence pathと接続されたことを証明する。
