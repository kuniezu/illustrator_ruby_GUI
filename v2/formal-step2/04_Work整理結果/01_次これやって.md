## blocker A: deterministic recovery exceptionがactual callback pathでは`transport-uncertain`になる

`renderedBridgeBody()`ではsource identity確認後、

`FormalAreaTextNativeRecoveryRuntime.converge(...)`

をobservation/native lifecycleのtry/catchより前に直接実行している。

したがって recovery中の

- duplicate ownership
- no-progress
- loop-limit
- coordinator/recovery deterministic error

などがthrowすると、BridgeTalk body自身がerror終了し、host側`bt.onError`へ落ちる。

`renderedBridge()`の`onError`は一律

`kind: "transport-uncertain"`

として返す。

一方、前completion report / catalog OBS-05 / shared checklistは「deterministic recovery failureはnative lifecycle failureとして扱い、transport uncertaintyはBridgeTalk transportに限定」としている。actual production callback pathと一致していない。

### 修正要件

安全性を下げずにactual pathを整理する。

1. recovery deterministic errorをgenerated body内で構造化できる場合は、recovery専用try/catchで捕捉する。
2. catch時点で`frame.note`をauthoritativeに再readでき、document path / UUID / source contents / exact note readbackを満たせるなら、current noteを含むstructured lifecycle/recovery failure resultとして`onResult`へ返す。
3. recoveryが途中でDOM/noteを変更した可能性がありauthoritative stateを安全に確定できない場合は、従来どおり`transport-uncertain`相当のfail-closedでよい。無理にretry-safeにしない。
4. mutation前のduplicate等、明らかにdeterministicかつsource stateが確定しているfailureを一律transport uncertaintyへ潰さない。
5. UIはdeterministic recovery failureとtransport result uncertaintyを区別する。ただしblind retry禁止が必要なケースは維持する。
6. report/catalog/checklistの説明をactual semanticsに一致させる。
