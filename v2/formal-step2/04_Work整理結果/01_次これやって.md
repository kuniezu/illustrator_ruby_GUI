## blocker A: unrelated source text editでvalid splitGuardまで全消去される

現行 `re-resolution.js` は `inheritedOccurrence(old,current)` で old occurrenceの reading / enabled / lineage 等を継承する一方、`splitGuard` を継承しない。

また `expandLocalRuns()` が既存split runを再構築するときのchildにもsplitGuardを付けない。

そのため、たとえば:

1. `再編集` が `split-hint-required`。
2. `再｜編集` へsplitし、childrenにsplitGuardがdurable保存される。
3. source textの**別の場所だけ**を編集する。
4. re-resolutionは当該split children自体をcontext/positionで正しく継承できてもsplitGuardを落とす。
5. reopen後、`wouldRestoreSplitBlocker()` がfalseになり隣接結合が再び可能。
6. merge後に同じ `split-hint-required` を復活させ得る。

前dispatchで追加した `source text re-resolution does not inherit stale splitGuard provenance` は「guardを全部捨てる」挙動をPASSにしており、**unrelated editでstill-valid provenanceを保持すべきケースを検証していない**。

### repair contract A

splitGuardを「source textが変わったら一律破棄」してはいけない。

- unchanged local split runがdeterministically re-resolveされ、そのsplitGuardの対象surface/range semanticが維持されている場合はguardを保持する。
- guard対象のsurface/range/lineageが変わった、ambiguous/not-found、またはguardの根拠がinvalidになった場合だけguardを失効する。
- re-resolutionがguessになる場合はguardを移植しない。
- unrelated source editでrequired merge guardが消えない。

単純な「old.splitGuardを常にcopy」も禁止。stale provenanceの誤継承を避ける条件を明示する。

## blocker B: geometry/reflowだけ変わるとsplitGuardを失効できず永久merge禁止になる

production entrypointは:

```js
stored = FormalMultiStore.read(cachedNote);
if (stored && stored.textSnapshot !== picked.text) {
    reResolution = FormalLongTextReResolution.reconcile(stored,picked.text);
    bundle = reResolution.bundle;
} else bundle = stored || FormalMulti.createFrame(picked.text);
```

つまりsource textが同じでAreaText width/height/reflowだけ変わった場合、re-resolutionは走らない。

一方merge guardは現在:

```js
if(FormalLongText.wouldRestoreSplitBlocker(bundle,[first.occurrenceId,second.occurrenceId]))
    fail("merge-would-restore-split-blocker");
```

で、current observation/plannerを一切見ずsplitGuard provenanceだけで恒久拒否する。

したがって:

1. 狭いAreaTextで `再編集` がline crossing → split required。
2. split/render/reopen成功。
3. 後でAreaTextを広げ、`再編集` が1行に収まるgeometryになる。
4. source textは同じなのでguardは残る。
5. mergeはcurrent geometryに関係なく永久に拒否。

これはpractical workflow上のdead-end。前reportの「guardを消す根拠がないので保持」は保守的だが、Gate D closureには不十分。

### repair contract B

**現在のobservation/planner evidenceでguardを再検証できる経路を設ける。**

推奨条件:

- merge前にguard対象のcombined surface/rangeをcurrent AreaText observationに対して安全にprobe/planできるなら、その結果で判断する。
- current evidenceが依然split-required → merge reject。
- current evidenceがmerged occurrenceとしてcomplete/no split requiredを明確に証明 → guardを解除してmerge許可。
- observation不足 / ambiguous / failed → fail-closed。推測で解除しない。

UIだけのforce-mergeやplanner条件緩和は禁止。

既存planner/orchestrationを再利用し、独自のline-crossing判定をUIに複製しないこと。

## lifecycle semantic to establish

splitGuardは永続boolではなく、少なくとも次を持つ/proveできる provenance として扱う。

- 何のoccurrence/rootに対するguardか
- どのsplit boundary evidenceが根拠か
- source text re-resolution後も同一semantic対象か
- current geometry observationでまだ有効か

必要以上のschema redesignは避けるが、source semanticとgeometry evidenceの両方でvalidityを判定できること。

## executable regressions — static match不可

最低限以下を追加・更新する。

1. **unrelated source edit preserves valid guard**
   - required split → child guardあり → source別箇所編集 → deterministic re-resolution → children guard保持 → merge reject。

2. **edit inside guarded run invalidates/requires re-resolution**
   - guard対象surface/rangeが変わる → stale guardをblind copyしない。

3. **ambiguous/not-found does not transfer guard**
   - fail-closed/unresolvedで誤identityへguard移植しない。

4. **geometry still requires split**
   - current observationでもline crossing → merge reject維持。

5. **geometry no longer requires split**
   - source text同一、reflow changed、current plannerがmerged candidate completeを証明 → merge許可。

6. **observation unavailable/uncertain**
   - guard解除せずmerge reject。

7. reopen/store roundtrip後も上記semantic同一。

8. ordinary/manual split/mergeは壊さない。

9. split→render→merge許可時のnative transition/retirement ownershipを確認。

10. merge拒否時はbundle/revision/selection/source note/native generation不変。

既存 `source text re-resolution does not inherit stale splitGuard provenance` は意味が広すぎるので、期待semanticに合わせて置換/分割すること。
