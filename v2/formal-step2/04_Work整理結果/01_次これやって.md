## blocker A: `retrySafe:false` の deterministic recovery failureでもpaletteが再保存を許す

`renderedBridge()` の `onError` は deterministic recovery failureについて

- `kind:"recovery"`
- `noteVerified:false`
- `retrySafe:false`

を返す。

しかし `Formal Multi Step2.jsx` の failure callbackは現在、save禁止にする条件を

`diagnostics.kind === "transport-uncertain"`

だけで判定している。

そのため `kind:"recovery", retrySafe:false` は通常の保存失敗として表示された後、`setSavePending(false)` によりsave buttonが再有効化される。これはcallback payload自身の `retrySafe:false` 契約と矛盾し、authoritative noteを持たないrecovery failure後のblind retryを許す。

### 修正要件

- UIのretry可否は `kind` 名だけでなく `retrySafe === false` を権威として扱う。
- `noteVerified:false && retrySafe:false` のrecovery failureは再保存不可にし、close/reopen/resync/recoveryへ誘導する。
- `noteVerified:true` のdeterministic failureでも、payloadが `retrySafe:false` ならblind retryしない。
- 将来retrySafe trueを導入する場合も明示契約がある場合だけ許可する。
- stateTextは `transport-uncertain` と `recovery blocked` を区別してよいが、安全性は同じくsave禁止。

---

## blocker B: `classifyFailure()` のauthoritative-note分岐がproduction pathに接続されていない

`FormalAreaTextNativeRecoveryRuntime.classifyFailure()` は

- authoritative snapshot取得成功 → `kind:"recovery", noteVerified:true`
- 取得不能 → `transport-uncertain`

という契約を持つ。

しかし現在generated BridgeTalk production bodyはこのhelperを呼んでいない。

actual productionでは `fail()` がerror markerをthrowし、host `bt.onError` がmessage prefixだけを見て分類している。そのため deterministic recovery failureは常に `note:null / noteVerified:false` となり、completion reportにある「authoritative note/readbackを確認できる場合は deterministic recovery result」という分岐はproductionでは成立していない。

### 修正要件

安全性を下げず、次のどちらかで契約を一意にする。

1. **推奨:** generated body内でrecovery preflightをtry/catchし、catch時にdocument path / UUID / source contents / source note exact readbackを再確認できた場合、`FormalAreaTextNativeRecoveryRuntime.classifyFailure()` 相当のstructured resultを `onResult` へ返す。確認不能ならfail-closed/transport-uncertain。
2. もしproductionでauthoritative-note deterministic resultを安全に作れないなら、その機能をreport/catalog/helperから外し「recovery throwはauthoritative state不明なのでblocked」と契約を縮小する。

reportとactual runtime semanticsを一致させること。helperを置いただけでproduction対応済みとしない。

## blocker C: generated `fail()` がrecovery以外のdeterministic preflight errorまで uncertainty markerへ変換する

現在generated bodyの `fail(m)` は `native-recovery-*` 以外をすべて

`recovery-state-uncertain:<original>`

へ変換してthrowする。

このため recovery開始前の

- origin-document-mismatch
- uuid lookup/source mismatch
- runtime-symbol-missing
- source-note-target-mismatch

等まで transport/recovery uncertaintyに潰れる。

fail-closedなので安全性は保たれるが、diagnostic truthfulnessとcallback classification契約が不正確。

### 修正要件

- recovery scope外のdeterministic preflight errorをrecovery uncertaintyへ改名しない。
- recovery中にauthoritative stateが不明になったerrorだけをuncertain扱いにする。
- identity/source mismatchは従来のdeterministic STOP理由を保持する。
- retry安全性は明示的に決め、deterministicだから自動retry-safeとはしない。
