## blocker A: native render成功後もrender evidenceがcompleteへ確定されない

現在の`saveRendered()`はBridgeTalk送信前に

`nextNote = FormalMultiStore.write(cachedNote, bundle)`

を作る。

production BridgeTalk bodyはplanner complete後、native lifecycle開始前に

`frame.note = next`

を書き、そのnoteをtransaction expectedNoteとして使う。native render / retire / finishが成功しても、最後はその時点の`frame.note`を返すだけで、planner成功結果をoccurrence-level `renderStatus=complete` へ反映したFormal Multi bundleを作り直していない。

そのため、再試行前のbundleが `failed` / `unresolved` / `pending` evidenceを持っていた場合、実際にはruby描画成功でもsource noteとpalette/reopen stateに旧evidenceが残り得る。top-level `bundle.renderStatus` も同様に旧状態を保持し得る。

### 修正要件

- native lifecycleが本当に成功し `finish` まで完了した後にのみ、render成功evidenceをsource noteへ確定する。
- current `frame.note` に含まれるnative manifest等を壊さないよう、`FormalMultiStore.write(String(frame.note), completedBundle)` のように現在noteをbaseに更新することを優先検討する。
- exact readbackを行う。
- eligibleかつ実際にplanner completeだったoccurrenceは `renderStatus=complete`、reason/boundary evidenceはcurrent成功状態に合わせてclearする。
- suppressed / unsupported / reading-unconfirmed 等、描画対象外occurrenceを虚偽のrender-readyにしない。
- top-level `bundle.renderStatus` もterminal成功と整合させる。
- callback直後paletteとclose/reopen後が同一であること。

## blocker B: native/lifecycle failure後にsource noteとpalette cachedNoteが分岐し、再保存が詰まり得る

native pathでは `frame.note=next` を行った後に、prepare / verify / activate / retire / finish が続く。

その後native errorになると現在は `lifecycleFailure(...)` を返し、host側 `bt.onResult` は `callbacks.failure(...)` へ送る。failure callbackにはauthoritative persisted noteが返らないため、palette側 `cachedNote` は旧値のままになり得る。

一方source `frame.note` は既に `next` またはnative transactionで更新されたnoteへ変化している可能性がある。

この状態でpaletteを閉じずに再度保存すると、次回BridgeTalkの `source-note-target-mismatch` を誘発し得る。

### 修正要件

- source noteを変更した後のterminal failureでは、palette側がauthoritative current noteへ追従できる契約にするか、安全に旧cached noteへ戻す。
- readingを安全に保存する既存方針を維持するなら、failureでもcurrent persisted noteを構造化payloadで返し、callback側で `cachedNote` とbundleを同期する方式を優先検討してよい。
- callback分類上の `transport failure` と `render/lifecycle failure` を混同しない。
- source noteが変化していないpre-send/identity failureは従来どおりfailureでよい。
- 「失敗後に同じpaletteからもう一度保存」が `source-note-target-mismatch` にならない回帰を追加する。

## blocker C: native failure時のrender evidence semanticsがterminal outcomeと一致しない

observation / planner noncomplete pathはSTATE-05までで正規化したが、planner complete後のnative failureは別経路であり、Formal Multi occurrence evidenceをcurrent failureへ正規化していない。

ただしnative lifecycleは段階により意味が異なるため、単純に全てfailedへしないこと。

### 必須の分類

1. **activation前 failure**
   - 新renderは未activate。
   - current attemptがfailedであることをpersisted evidenceへ反映できる。
   - abort/cleanup契約を維持する。

2. **activation後 retire/cleanup/finish failure**
   - 新renderが既にactivateされている可能性がある。
   - 「render failed」と虚偽表示しない。
   - 既存方針どおりpost-activation cleanup failureをrollback扱いにしない。
   - render outcomeとlifecycle cleanup outcomeを分離してdiagnostic/stateへ残す。

どちらもpalette/source note/reopen stateが矛盾せず、retry可能であることを回帰化する。

## blocker D: semantic edit後もbundle-level renderStatusが旧terminal値のまま残り得る

`setOccurrenceReading()` / `setOccurrenceEnabled()` はsemantic edit時にoccurrence evidenceをpendingへresetするが、frame-level `bundle.renderStatus` は更新していない。

前回persistされたtop-level statusが `failed` / `unresolved` の場合、入力を修正して新しいplan待ちになってもbundle-level statusだけ旧値が残る。

### 修正要件

- render-plan前提を変えるsemantic edit / split / mergeではframe-level statusも `pending` 相当に戻す。
- no-op editor commitではoccurrence evidenceと同様、frame-level statusも不必要に変更しない。
- terminal planner/native result確定時にはframe-level statusをcurrent outcomeへ揃える。

## blocker E: production runtime source preflightが`multiStore`を検証していない

`renderedBridgeBody()`は `sources.multiStore` を使って `multi-store.js` を`$.evalFile`するが、`verifyRuntimeSources()` の必須namesに `multiStore` が入っていない。

現状repoにはファイルがあるため常時失敗する問題ではないが、production bodyの依存ファイルとpreflight契約が一致していない。同じ「preflight PASSなのにBridgeTalk内で停止」を避けるため今回まとめて閉じる。

### 修正要件

- generated BridgeTalk bodyがevalするproduction dependency一覧と `verifyRuntimeSources()` の検証一覧を一致させる。
- `multiStore` 欠落時はsend前に明示failureとなる回帰を追加する。
- 他にも同様のeval dependency漏れがないか、この機会に一覧比較する。

## 一括state-machine回帰

今回は個別assertionだけでなく、可能な範囲でterminal outcome matrixを1本または少数のintegration regressionへまとめる。

最低限、次を証明する。

### Scenario 1: split-hint-required → local split → 再保存成功

- confirmed `再編集` がactual line boundaryをまたぐ。
- planner unresolved + exact local boundary。
- persisted note / callback / reopen / navigation no-opでboundary保持。
- local split後childrenはreading未確認。
- child readingを修正・確認するとsemantic editとしてpendingになる。
- 再保存planner complete → native lifecycle success。
- terminal note / palette / reopenでcurrent render evidenceがcompleteで一致。

### Scenario 2: native failure → retry

- planner complete後、activation前native failureを注入。
- source note / cachedNote / bundleが矛盾しない。
- persisted render evidenceがcurrent failureを表す。
- 同じpaletteからretryして `source-note-target-mismatch` にならない。

### Scenario 3: post-activation lifecycle failure

- activation後のretire/cleanup/finish failureを既存test seamで再現可能なら追加する。
- render outcomeとcleanup outcomeを混同しない。
- rollback前提へ戻さない。
- authoritative noteをpalette/reopenが共有する。

### Scenario 4: semantic edit/no-op

- semantic editはoccurrence + frame statusをpendingへreset。
- no-op navigation/saveEditorはcurrent evidenceを保持。
