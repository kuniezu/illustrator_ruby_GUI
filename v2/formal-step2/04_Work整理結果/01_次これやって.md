## blocker A: production `recoverNative()` がrecoveryをterminalまで収束させない

現在のgenerated BridgeTalk内 `recoverNative(note)` は `FormalAreaTextNativeRecovery.restart()` を1回だけ呼び、

- `cleanup-discarded`
- `cleanup-retirement`
- `finish-operation`

のいずれか1 actionだけ実行してreturnする。

一方、今回追加した executable test `terminal-recovery-state-machine.cjs` 自身は、

`cleanup-discarded → restart → cleanup-retirement → restart → finish-operation`

と複数回 `restart()` して初めて `finished/recoverable` へ到達している。

つまりtestが証明しているdesired sequenceとproduction helperの実装が一致していない。

### 直接起こり得る失敗

post-activation failureで cleanupQueue + retirementQueue が残る場合、production saveは最初の`cleanup-discarded`だけ済ませてreturnし、そのまま新requestの`beginOperation()`へ進む。manifestにはまだ `operation.phase="activated"` が残るため、`operation-already-active` になり得る。

retirementQueueだけ残る場合も、`cleanup-retirement`後にoperationをfinishせず新requestへ進むため同様。

operationなしでcleanup/retirement queueだけ残るケースでも、1 actionしか処理しないため「全recovery完了前に新operation開始」の余地がある。

## 今回やること

### 1. production recoveryをbounded convergence loopにする

- new practical native operationを始める前に、persisted manifestをterminal/recoverableまで収束させる。
- 各stepごとにmanifestをdurable updateし、その最新noteを次stepのexpected noteにする。
- recovery action後は必ず最新manifestを再readし、`FormalAreaTextNativeRecovery.restart()`を再評価する。
- `cleanup-discarded → cleanup-retirement → finish-operation` のようなmulti-step chainを1 save preflight内で完了させる。
- operation null + cleanup/retirement queueのchainも同様に全て処理してから新requestへ進む。
- infinite loop防止の明示上限を置き、同じmanifest/actionが進展しない場合はfail-closed。
- duplicate identityは従来どおりSTOP。
- missing physical outputはalready removedとしてdurable queueから除去。
- source/unmanaged objectは絶対に触らない。

### 2. executable regressionをproduction helper相当へ接続

現在の`terminal-recovery-state-machine.cjs`はpure state machineを手動で複数回進めており、generated `recoverNative()`が同じ収束を実行することを証明していない。

最低限、production-equivalent helper/harnessで次を実行assertする。

- activated + cleanupQueue + retirementQueue → 1 recovery preflight call → operation null / queues empty。
- activated + retirementQueue only → 1 recovery preflight call → operation null / queues empty。
- prepare / verified operation → abort + discarded cleanup → operation null / queues empty。
- operation null + cleanupQueue + retirementQueue → all queues empty before new begin。
- recovery完了直後に新request `beginOperation()` が成功する。
- duplicate identityは新requestへ進まずfail-closed。
- durable noteが各stepで前stepのresult noteをexpected noteとして使用する。

static regexだけでは完了扱いにしない。

### 3. recovery progress diagnostics

- stage logへ各recovery actionとrequestId、found/missing件数、terminal到達を残す。
- manual-required / no-progress / loop-limitは通常のrender failureと混同しない。
- deterministic recovery failureを可能なら`transport-uncertain`とは区別する。BridgeTalk transport自体が不確定な場合だけuncertainにする既存安全方針は維持する。

### 4. previous scenarioをまとめて再確認

以下を一続きで再監査する。

`split-hint-required → boundary persist → reopen/no-op → local split → child reading確認 → rerender → terminal complete`

`verify failure → single abort → retry`

`post-activation cleanup failure → persisted recovery state → close/reopen → recovery全収束 → next request success`

`suppress → reopen → re-enable → frame/occurrence pending → rerender success`

`transport uncertain → blind retry禁止 → reopen/resync → recovery全収束後のみretry`
